# 投标 Agent MVP-v1.5.5 易用性与标书质量打磨方案

> 更新时间：2026-06-17
> 当前阶段：实现收口；P0-A/P0-B 已落主干，P0-C 与 P1-A（Top3 待办减负、候选证据解释）已完成本地实现并验证，待整体验收。
> 版本定位：1.6 半自主编排前的打磨专项，不扩 AI 决策边界，重点提升“人自己操作也顺”和“导出的标书更可靠”。
> 本质：**把「标书内容打磨主轴」的后端确定性结果（覆盖/报价/导出快照）产品化到工作台与导出入口**——不新建判断规则，只把已落地的检查聚合成人能读懂的“提交前状态”。
> 承接关系：承接 MVP1.4 易用性、MVP1.5 企业资料 RAG 和“标书内容打磨主轴”；为 MVP1.6 的“推进助手”铺路。

## 0. 核心判断

MVP1.6 的半自主编排会把现有流程串起来自动跑，因此它会放大当前链路里的优点，也会放大卡点。

如果现在人工链路里仍存在“下一步不清楚、质量风险看不见、导出前心里没底、候选证据不够可信、浏览器链路未验收”的问题，那么 1.6 的一键推进会变成新复杂度。MVP1.5.5 要先把这些问题收口，让 1.6 变成加速器，而不是额外的概念负担。

一句话目标：

> 在不新增自动决策能力的前提下，把系统打磨成“用户知道下一步、知道风险、知道导出的文件能不能投”的产品状态。

## 1. 版本目标

MVP1.5.5 重点解决四类问题：

1. **易用性**：用户进入项目后能快速知道当前最该处理什么，不需要在多个 Tab 之间猜。
2. **标书质量**：L1–L4 的风险、缺口、评分覆盖、偏离/报价异常不只出现在 docx 里，也能在工作台里被提前看见。
3. **导出信心**：导出前明确展示本次会生成什么、会嵌入什么、还剩哪些占位或待确认项。
4. **1.6 前置稳定性**：补齐核心浏览器验收和样张回归，让后续半自主 Agent 调用的人工链路足够稳定。

## 2. 不纳入本版本

MVP1.5.5 不做以下事情：

1. 不做自动证据绑定；候选证据仍需人工采纳。
2. 不做自动修改草稿或自动确认资质结论。
3. 不新增多 Agent 编排、tool-calling 循环或 `assist_evidence` 后台任务；这些进入 MVP1.6。
4. 不做生成式报价建议；仅展示现有确定性报价/预算校验结果。
5. 不做技术标深度生成、净化产品选型、图纸/示意图或外部签章提交集成。
6. 不为追求“看起来智能”而弱化现有 No-Go、事实核查、导出预检和人工确认门禁。

## 3. 需求范围草案

> **贯穿项（不单列为功能）——核心浏览器验收**：浏览器端核心链路验收不是某个 P0 功能，而是**每个 P0/P1 模块的收尾完成标准**——以"仓顶"固定样张跑通"首页下一步 → 项目工作区 → 证据推荐 → ContextPack → 草稿审阅 → docx 导出"，并据此补齐既有版本明确登记的前端验收债：MVP1.3「剩浏览器端联调与章节级目录编辑增强」、MVP1.4「P0+P1 前端完成、浏览器端验收待补」、MVP1.5 RAG 候选证据链路的浏览器端确认。P0 发布必须先过核心链路脚本/浏览器验收；P1 功能进入完成状态前补齐对应断言。

## 4. 标书质量体检口径

体检不是新增一套判断规则，而是把现有确定性结果汇总成一个用户能读懂的“提交前状态”。

**枚举不分叉（硬约束）**：体检三档**不是新枚举**，而是复用与 `ContextPack readiness(pass/warn/block)` 一致的严重度语义；体检本身可由覆盖、报价、事实冲突和导出门禁独立推导，不要求一定存在 ContextPack。后端继续用 `pass/warn/block`，仅在面向用户的文案层映射成下表三档；前端/用户只见一套三态。

| 体检档（对用户） | 等价后端档 | 触发条件 | 用户动作 |
| --- | --- | --- | --- |
| 可继续 | pass | 未发现硬阻断，可能有普通待确认项 | 可进入审阅/导出 |
| 需复核 | warn | 评分缺口、待补事实、页码待更新、候选证据未采纳等 | 建议先处理，不阻断内部稿 |
| 阻断 | block | 废标风险、强制材料缺失、事实冲突、No-Go 未接受、正式导出门禁失败 | 阻止正式稿导出，或明确只允许内部稿 |

> 取档规则：按严重度取最高档，任一为 block 即 block；否则任一为 warn 即 warn；全 pass 才 pass。聚合逻辑落后端，不散到前端。

体检来源优先复用：

1. `tender_compliance_coverage.compute_coverage()`：L1/L2/L3 覆盖和废标风险。
2. `tender_pricing.build_pricing_report()`：报价算术、预算/最高限价校验。
3. ContextPack readiness checks：商务/资格草稿输入是否可用。
4. Draft coverage review / fact checks：草稿覆盖率、事实冲突、缺证据。
5. `tender_format_export` source snapshot：材料嵌入、PAGEREF、导出诊断。

## 5. 导出前确认口径

导出前确认页/弹窗应回答五个问题：

1. **这次导出什么版本**：审阅版还是正式版。
2. **会带哪些材料**：已确认、可嵌入的证照/证明/证据材料清单。
3. **哪些评分点已覆盖**：评分索引是否能定位到章节/附件/材料。
4. **还有什么风险**：占位字段、缺材料、页码待更新、报价异常、事实待确认。
5. **用户现在能做什么**：继续导出、回去补材料、先生成内部稿、取消。

**强制性（已拍板）**：正式版（submission）导出**必须先过确认 gate**——体检为 `阻断` 时拦截正式导出，只能改导内部稿或回去补缺；审阅版（review）**不强制**，确认页仅作信息展示，允许带待办/占位直接导出。

导出确认的底线：

- 不臆造页码、材料、事实和报价。
- 正式版不能隐藏硬阻断；审阅版可以保留待办和占位。
- 对 Word 域/PAGEREF 的限制要说清楚：页码由 Word/LibreOffice 分页引擎更新，无法定位的项保持可见缺口。

## 6. 与 MVP1.6 的交接

MVP1.5.5 完成后，1.6 的“推进助手”可以直接复用这些稳定表面：

| 1.5.5 产物 | 1.6 复用方式 |
| --- | --- |
| 质量体检 | Agent 推进后的结果摘要和待办来源 |
| 导出前确认 | Agent 不直接导出正式稿，只把阻断和可导出状态推给人 |
| 待办优先级 | Agent 选目标项时的排序依据 |
| 候选证据解释 | Agent 就地建议的展示基础 |
| 样张回归 | 1.6 接入后的回归样本 |

也就是说，1.5.5 要先把“建议/缺口/阻断”的语言统一，1.6 只负责自动触发和串联，不重新发明用户要理解的概念。

## 7. 验收标准草案

1. 用户进入项目工作区后，**一处**可见当前标段质量档（可继续/需复核/阻断）与关键风险，无需切 Tab。
2. 质量体检覆盖 L1 合规、L2 评分、L3 偏离/报价、L4 待确认叙述和导出阻断**五类全到位**；体检档与后端 `pass/warn/block` 取最严档一致（有单测覆盖映射）。
3. 导出前确认页**必含**字段：导出模式、将嵌入材料清单、评分索引状态、剩余占位计数、阻断项；正式版在 `阻断` 档被拦截（有用例覆盖拦截路径）。
4. 硬阻断不会被包装成“可提交”；审阅稿和正式稿边界清晰（正式版强制 gate、审阅版仅展示）。
5. 候选证据面板对每条候选能给出推荐理由、来源引用、风险和“采纳后覆盖哪个条款”四要素；已用单测与脚本化浏览器断言覆盖。
6. 首页/工作区待办**默认只突出 ≤3 件**关键动作，排序权重见 §4 取档规则与 §9 权重。
7. 仓顶/演示固定样张链路以**脚本化**浏览器用例跑通；当前脚本固化断言包括：服务可用、目标项目可进入、质量体检条可见、待办队列默认 ≤3 项、待办来源标签可见、展开/收起有效、候选证据解释四要素可见、审阅版/正式版导出确认字段齐全、正式版阻断时主按钮禁用。后续如要产出并检查 docx 内容，可在该脚本基础上继续追加下载与文件诊断断言。
8. `make mvp1-check` 保持通过；新增聚合/排序/状态映射逻辑必须有单测；体检聚合接口 P95 时延有基线（拆任务时定阈值）。

## 8. 工程约定

1. 优先复用现有后端服务和数据，不另建一套质量判断体系。
2. 如需新增接口，优先考虑薄聚合接口，例如“section quality summary”，不要把业务规则散落到前端。
3. 面向用户的状态文案可以白话化，但后端枚举/API 语义保持稳定。
4. 新前端能力应拆成独立组件，不继续无边界堆进主页面。
5. 质量体检和导出确认只提供建议、阻断和解释，不自动替用户确认事实或绑定证据。
6. 对大文件、证照图片和 PDF 渲染保持按需加载，避免为了体检做全量 I/O。

## 9. 待讨论问题

已拍板（本稿已收口，不再讨论）：

- **导出前确认强制性**：正式版强制 gate、审阅版仅展示（见 §5）。
- **样张回归形态**：直接做脚本化浏览器用例，不做手工清单（见 §7.7）。
- **状态枚举**：复用 `pass/warn/block`，不造新枚举（见 §4）。
- **候选证据解释生成方式**：P1 先用检索命中字段 + 规则文案生成，LLM 重写留到 1.6 就地建议一起做。

仍待评审拍板：

1. 质量体检组件放在工作区总览、草稿页、导出页，还是三处共用同一组件实例？（倾向：一个后端聚合 + 一个可复用组件，三处嵌入。）
2. P0 是否新增后端聚合接口（如 `GET .../section-quality-summary`），还是先由前端组合现有接口？（倾向：薄聚合接口，避免业务规则散到前端，见 §8.2。）
3. “当前最该处理的 ≤3 件事”的排序权重：废标风险 > 正式导出阻断 > 评分缺口 > 待确认事实/缺证据 是否作为默认？（倾向：按此默认，后续可调。）

## 10. 初步建议

建议先按最小闭环推进：

1. **P0-A：标书质量体检聚合**，把已有检查结果按 §4 取档规则统一成可读摘要（含状态映射单测）。
2. **P0-B：导出前确认**，把体检结果接到 docx 导出入口，正式版接入阻断 gate。
3. **P0-C：仓顶样张脚本化验收**，已完成浏览器脚本入口与核心断言；后续可扩展 docx 下载/诊断断言。
4. **P1-A：待办减负 + 候选证据解释优化（规则文案版）**，Top3 聚合与候选证据四要素解释均已完成本地实现并纳入单测/浏览器回归。

完成本地整体验收后，再进入 MVP1.6 的证据绑定推进助手，风险会小很多。
