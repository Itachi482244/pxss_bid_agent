# 投标 Agent 易用性优化方案

> 版本：v0.1（讨论稿）
> 日期：2026-06-06
> 范围：基于 MVP1.3 当前线上界面的实际走查，聚焦终端用户易用性（usability），兼顾影响迭代速度的工程可维护性。
> 性质：现状评估 + 优化建议清单 + 决策记录。
> 归属：本方案的 P0/P1 已收敛为 **MVP1.4 易用性优化**（详见 `docs/投标Agent MVP-v1.4需求规划与开发进度.md`）；P2（App.tsx 拆分）暂缓不进排期；原 MVP1.4 的 RAG 规划顺延为 MVP1.5。

---

## 1. 背景与评估方式

本方案基于对当前运行版本（前端 `localhost:5173`，后端 MVP1.3）的实际界面走查得出，覆盖以下主要界面/流程：

- 首页「工作总览」（项目列表 + 统计卡片 + 待办提醒）
- 任务中心 / 7 步工作台（上传文件 → 等待系统 → 质检处理 → 审阅条款 → 绑定资料 → 资格/技术 → 上下文包）
- 异步解析/生成进度（进度条 + 待办队列卡片）
- 商务草稿块列表（覆盖标签 / 操作按钮 / 强制措辞「待确认」块）
- ContextPack 指令编辑器、目录编辑器弹窗

评估视角：以「一线招标/投标人员（非本系统设计者）」为主要用户，判断其能否低门槛地完成"看懂现状 → 知道下一步 → 顺利操作 → 得到可信结果"。

---

## 2. 总体判断

**流程骨架完整、专业，但当前易用性处于"内部熟手可用"的水平，对一线用户仍有明显门槛。**

- 优点：7 步流程导航 + 异步任务中心 + ContextPack 驱动的结构化草稿，"先冻结素材再生成、全程可回溯"的设计在投标场景方向正确，质量门禁（事实核查、导出预检、No-Go 拦截）严谨。
- 主要差距：信息组织偏向"完整暴露系统内部状态"，缺少面向用户的**任务收敛、术语解释、操作聚焦和等待反馈**。

---

## 3. 分维度痛点（按影响排序）

### 3.1 首页信息过载（高）
- **观察**：「工作总览」一次性铺开全部项目（走查环境约 50 条），未见明显的状态分组、筛选、分页入口；统计卡片（0 待补充 / 50 进行中 / 11 待审阅 / 47 ...）与下方长列表割裂。
- **问题**：用户进入后第一眼无法判断"现在该处理哪个项目"；真实使用一段时间后，活跃项目会淹没在历史项目长列表中。

### 3.2 术语门槛（高）
- **观察**：界面直接暴露大量系统内部概念——ContextPack / 上下文包、草稿事实、强制措辞、轻量重建、No-Go、矩阵版本、needs_confirm 等，且几乎没有 tooltip 或首次引导解释。
- **问题**：非技术招标人员需要额外培训才能理解这些词，增加上手成本与误操作风险。

### 3.3 "该我做什么"不明确（高）
- **观察**：待办通过右侧红色卡片堆叠呈现（如 矩阵版本 14 / 高风险 2 / 草稿事实 1），优先级靠颜色与文案区分。
- **问题**：缺少统一的"待我处理"收件箱视图；用户需自行在多个卡片/步骤间判断先做哪一项。

### 3.4 草稿块列表信息密度过高（中）
- **观察**：每个草稿块挂一排标签（已覆盖 / 条款 1 / 证据 0 / 原文 / 审阅台）并重复出现 编辑 / 通过 / 需补证 操作；强制措辞以紫色「待确认强制措辞」块混排在长列表中。
- **问题**：扫读困难；逐条确认强制措辞需要在长列表里人工定位紫色块，缺少"只看待确认/待补证"的过滤与聚焦入口。

### 3.5 异步等待反馈不足（中）
- **观察**：解析中显示进度条（如 18%）+ "当前不需要人工操作，可切换页面"。
- **问题**：文案已说明可离开，但缺少预计耗时与完成提醒，用户仍倾向于停留干等；长任务缺乏阶段性可读进度。

### 3.6 工程可维护性间接拖累易用性迭代（低/工程）
- **观察**：`frontend/src/pages/App.tsx` 单文件约 **10131 行**，`components/` 目录仅 3 个组件，绝大部分 UI 逻辑集中在单文件。
- **问题**：任何 UI 调整改动面大、回归风险高、迭代慢，长期会拖累易用性优化的落地速度。

## 4. 优化建议（含问题→方案→预期收益）

### P0-1 首页项目列表治理（项目为主轴）+ 待办聚合（次要）（对应 3.1 / 3.3，§6 第 2 条）
- **方案（主）**：以项目列表为首页主结构，做好治理——
  - 「进行中 / 待我处理 / 已完成」状态分组或筛选；
  - 关键字搜索 + 分页（或虚拟滚动），保证活跃项目易定位；
  - 每个项目行直观呈现"当前阻塞/下一步"，点进去直达对应操作页。
- **方案（辅）**：跨项目"我的待办"作为**次要入口**（顶部提醒角标/可选聚合视图），把分散的矩阵版本/高风险/草稿事实等待办按优先级聚合，但不取代项目主视图。
- **预期收益**：用户进入后快速定位活跃项目并知道"先做什么"，显著降低导航成本。

### P0-2 术语白话化 + 必要处 tooltip（对应 3.2，§6 第 3 条）
- **方案（主）**：把面向用户的展示文案统一换成大白话（见 §6 第 3 条映射表），**仅改前端展示文案，不动后端字段/模型/API**。
- **方案（辅）**：确需保留的专业概念，在首次出现处加问号图标 + 悬浮解释，并集中维护一份术语对照表。
- **示例补充解释**：
  - 必须原样写入的内容（原"强制措辞"）＝ 你指定必须原样写入草稿的句子（仍需通过事实核查与人工确认）；
  - 快速重新生成（原"轻量重建"）＝ 仅改写作要求、复用已有事实，快速产出新版本。
- **预期收益**：降低培训成本，减少因误解概念导致的误操作。

### P1-1 草稿块列表过滤 + 指定内容确认（逐条查看 + 受保护批量）（对应 3.4，§6 第 4 条）
- **方案**：
  - 列表顶部增加状态过滤（全部 / 待确认的指定内容 / 待补证 / 待覆盖）；
  - 提供"逐条查看"聚焦流，在待确认项之间快速跳转，系统记录每条是否已查看；
  - **受保护的批量确认**：仅对"已查看"的项生效，未查看项阻止批量并提示；批量驳回需附原因；
  - 降低单块标签密度（次要标签收进展开/悬浮）。
- **预期收益**：审阅效率提升，且保留逐条核验的安全性，降低漏确认导致的导出阻塞。

### P1-2 异步任务预计耗时 + 完成提醒（对应 3.5）
- **方案**：进度条旁显示预计剩余时间/阶段说明；任务完成时通过站内通知或角标提醒，支持"离开后回来一眼看到结果"。
- **预期收益**：减少干等，提升长任务场景下的体验与信任感。

### P1-3 管理层宏观看板（对应 §6 第 1 条结论新增）
- **方案**：新增面向老板/负责人的管理视图，与一线操作视图分层，呈现经营级聚合指标，例如：在投项目数与状态分布、待办积压、参标 Go/No-Go 分布、按时间的命中率/中标趋势、风险项汇总等；支持按团队/成员/时间维度下钻。
- **预期收益**：管理层无需进入具体项目即可掌握全局，辅助参标决策与资源调度。
- **依赖**：需要先明确指标口径与数据来源（部分指标如中标结果可能需新增数据录入）。

### P2-1 渐进式拆分 App.tsx（对应 3.6，工程向）——【暂缓，不进当前排期】
- **方案**：按功能域（首页/工作台/草稿/ContextPack）逐步抽离为独立组件与 hooks，先抽高频改动区，不做一次性大重构。
- **预期收益**：后续易用性迭代更快、回归风险更低。
- **当前决策（§6 第 5 条）**：暂缓；新功能开发时可顺手收敛，但不专门排期。

## 5. 落地优先级建议

| 优先级 | 事项 | 主要收益 | 粗估成本 |
|---|---|---|---|
| P0 | 首页项目列表治理（项目为主轴）+ 待办聚合(辅) | 快速定位活跃项目、知道"做什么" | 中 |
| P0 | 术语白话化 + 必要处 tooltip（仅改前端文案） | 降低上手与误操作 | 低 |
| P1 | 草稿块状态过滤 + 指定内容确认（逐条查看 + 受保护批量） | 审阅提速、减少导出阻塞、保留安全性 | 中 |
| P1 | 异步任务预计耗时 + 完成提醒 | 改善等待体验 | 低-中 |
| P1 | 管理层宏观看板 | 管理层掌握全局、辅助决策 | 中（依赖指标口径） |
| P2 | 拆分 App.tsx | 提速后续迭代 | 中-高（暂缓，不进当前排期） |

## 6. 待讨论问题

1. 主要目标用户画像是否就是"一线招标/投标专员"？是否还要兼顾"标书复核/负责人"等角色（影响收件箱与权限设计）？
   - **结论（2026-06-06）**：**全角色覆盖**——一线投标专员、标书复核/审核人、项目/部门负责人、企业资料/资质管理员，以及"一人身兼多角色"的小团队场景都要支持。
   - **新增需求**：面向**老板/管理层的宏观看板**，能看整体经营信息（如在投项目数、待办积压、参标 Go/No-Go 分布、命中率/中标趋势等），与一线操作视图分层。
   - **设计含义**：收件箱与权限需按角色分层；首页要区分"操作型视图（我的待办）"与"管理型视图（宏观看板）"；管理层看板作为新增建议项纳入清单（见 §4 新增 P1-3）。
2. 首页是项目维度还是任务维度优先？是否需要"我的待办"跨项目聚合视图？
   - **结论（2026-06-06）**：**项目维度为主轴**——先选/定位项目，再看该项目内的待办与进度（接近现状心智，符合招标"以单个项目为单位推进"的工作方式）。
   - **设计含义**：
     - P0-1 调整为"以项目列表为主 + 项目内待办聚焦"，跨项目的"我的待办"聚合**降级为次要入口**（如顶部提醒角标或可选视图），不作为首页主结构；
     - 首页项目列表的**治理（状态分组、筛选、搜索、分页）成为重点**，确保活跃项目易定位；
     - 管理层宏观看板（P1-3）作为**独立入口/视图**，不与一线项目首页混用。
3. 术语解释走 tooltip 轻量方案，还是配套一个"新手引导/帮助中心"？
   - **结论（2026-06-06）**：**优先把术语换成大白话**，减少专业黑话；仅在确实需要保留专业概念处补 tooltip。
   - **原则**：仅改"面向用户的展示文案"，**后端数据模型/字段名/API 不变**，避免牵动既有逻辑与测试。
   - **初步术语白话化映射（待逐一确认）**：
     | 现术语 | 建议白话 |
     |---|---|
     | ContextPack / 上下文包 | 投标素材包 / 本节资料与要求 |
     | 强制措辞 | 必须原样写入的内容 / 指定原文 |
     | 轻量重建 | 快速重新生成（沿用已有事实） |
     | No-Go | 不建议参标 |
     | 矩阵版本 | 合规清单版本 |
     | needs_confirm / 待确认强制措辞 | 待确认的指定内容 |
     | 草稿事实 | 草稿中的关键数据/事实 |
   - **设计含义**：P0-2 由"加 tooltip"升级为"先做一轮术语白话化（统一文案）+ 必要处 tooltip"。
4. 强制措辞逐条确认是否需要批量操作（全部确认/批量驳回）？
   - **结论（2026-06-06）**：**允许批量确认，但带保护**——只有用户已"逐条查看过"的指定内容才可纳入批量确认；未查看过的不允许直接批量通过，避免无脑确认带来风险。
   - **设计含义**：
     - 提供"逐条查看"流（在待确认项之间快速跳转），系统记录每条是否已被查看；
     - 批量确认仅对"已查看"集合生效；对"未查看"项给出明确提示并阻止；
     - 批量驳回可放开（驳回是更安全的方向），但需附驳回原因。
5. App.tsx 拆分的节奏：随易用性需求顺带拆，还是单独排一轮工程治理？
   - **结论（2026-06-06）**：**暂不专门拆分**，优先把易用性功能做出来；拆分以后再视情况安排。
   - **设计含义**：P2-1 标记为"暂缓"，不进当前排期；新功能开发时在不增加大额成本的前提下可顺手收敛，但不强制。
