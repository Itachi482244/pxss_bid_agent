# 投标 Agent AI 能力版本路线图

> 更新时间：2026-05-28
> 目的：明确后续版本中哪些投标工作适合由 AI 辅助执行、如何控制风险，以及 MVP1.1 / MVP1.2 / MVP1.3 的能力边界。
> 核心原则：AI 可以扩大处理能力，但不能扩大责任边界。
> 当前状态：MVP1.1 P0 + P1 已完成主体开发；MVP1.2 聚焦商务/资格草稿生成 ContextPack、分章节提示词和生成稿审阅；MVP1.3 聚焦企业资料 RAG、Embedding/Rerank 和候选证据推荐。技术标、净化产品、图纸/OCR、多 Agent 和报价辅助进入长期规划，不排入具体 MVP 版本。

## 1. 基本判断

投标是高精度、高风险、强合规场景。AI 在这个场景中最擅长的不是直接替人做最终决策，而是在复杂信息中完成定位、分类、对比、解释和草稿化。

因此，本项目的核心不是提供一个让 AI 自由发挥的聊天窗口，而是建设一个高质量的投标上下文工作台：

1. 文件有版本。
2. 条款有来源。
3. 证据有资料。
4. 草稿有引用。
5. 风险有解释。
6. 动作有审批。
7. 过程有审计。

未来 AI 能力应运行在这些上下文之上，而不是绕开它们。

本项目对生成链路的最高指导原则是：

> 生成标书前的一切流程，都是为了给最终模型生成正式产出提供完美上下文。

这里的“完美上下文”不是指信息无限多，而是指上下文满足以下条件：

1. 完整：覆盖招标原文、矩阵条目、企业资料、证据绑定、资格判断、事实校验和人工确认。
2. 干净：过滤无关公告信息、重复条目、污染文本、过期资料和未授权资料。
3. 可追溯：每个条款、事实、证据和生成段落都能回链到文件版本、原文片段或企业资料。
4. 可裁剪：不同生成任务只取需要的上下文，避免把无关材料塞进模型窗口。
5. 可校验：金额、日期、证书编号、人员、业绩、技术参数等事实可被再次验证。
6. 有边界：高风险、强制响应、资格判断、审批和最终承诺必须保留人工关口。

换句话说，投标 Agent 的价值不是“会聊天”，而是：

> 基于受控上下文、受控工具、受控权限和人工关口，辅助投标人员少漏项、少翻文件、少编错、少返工。

## 2. AI 能力分级

| 等级 | 能力类型 | 典型任务 | 风险判断 | 版本建议 |
| --- | --- | --- | --- | --- |
| L1 | 读取定位 | 找条款、找证据、找差异、找版本变化 | 低 | MVP1.1 优先 |
| L2 | 分类排序 | 条款分类、证据排序、风险初判、处理优先级 | 低-中 | MVP1.1 优先 |
| L3 | 解释建议 | 推荐原因、风险说明、审批摘要、下一步建议 | 中 | MVP1.1 / MVP1.2 |
| L4 | 草稿生成 | 商务/资格草稿、资料改写 | 中-高 | MVP1.2 起；技术响应草稿进入长期规划 |
| L5 | 自动决策/动作 | 审批、签章、提交、最终参标决策 | 极高 | 不做或长期禁止 |

等级越高，约束越强：

- L1/L2 可以更多依赖模型辅助，但必须回链来源。
- L3 必须基于已有上下文生成解释，不允许无来源发挥。
- L4 必须逐段引用证据，并经过事实校验和人工复核。
- L5 不应进入近期产品范围，尤其不能自动提交、自动签章或替人做最终承诺。

## 4. MVP1.1：AI 做读标、拆分、分类和解释

MVP1.1 的目标不是生成完整标书，也不正式接入 embedding/rerank，而是先把 Chat/LLM 模型接入、PromptOps、读标增强和人工审阅纠错闭环做好。

当前已完成：

1. 模型配置中心：设置页配置 Chat/LLM 的 `base_url`、`api_key`、`simple_model`、`complex_model`，配置写入 DB，环境变量兜底。
2. PromptOps 底座：prompt registry、版本号、hash、schema 校验和黄金样本回归。
3. 条款语义分类：资格、强制、评分、技术、格式、截止时间等。
4. 关键字段辅助抽取：截止时间、预算/限价、格式要求等进入待确认字段或矩阵项。
5. 风险等级初判：模型初判，规则兜底，高风险必须人工确认。
6. 技术响应结构化：识别洁净等级、风量、过滤级别、压差、安装、调试、验收、售后等方向性字段。
7. 矩阵审阅视图：左右对照招标原文和合规条目，支持定位、筛选和确认。
8. 人工审阅纠错：人工划选补漏、相似补票、文本 Diff 高亮、重复项关联和级联确认。

暂未完成且不塞回 MVP1.1 P0/P1：

1. 提交前核验摘要的模型生成。
2. 审批意见草稿的模型生成。
3. 企业资料真实 RAG 和模型重排。
4. 技术标核心章节生成。
5. PDF 原文式矩阵审阅适配、扫描件/OCR 和复杂版式进入长期规划或生产化专项。

MVP1.1 必须保留的边界：

- 不生成完整技术标核心章节。
- 不做最终产品选型承诺。
- 不正式接入 embedding/rerank。
- 不做企业资料真实 pgvector RAG。
- 不做自动审批、自动提交、自动签章。
- 所有 AI 输出必须能回链到项目版本、招标原文、企业资料或系统核验结果。

## 5. MVP1.2：AI 做商务/资格草稿 ContextPack 和生成稿审阅

MVP1.2 的目标是把 MVP1.1 形成的“招标原文 + 合规矩阵 + 人工确认 + 已绑定证据”正式转化为可预览、可审计、可校验的 ContextPack，并基于 ContextPack 生成可审阅的商务/资格候选稿。本版本不接真实 RAG、Embedding 或 Rerank，避免生成链路被检索质量拖住。

### 5.1 P0：商务标生成上下文包和分章节提示词

建议能力：

1. 商务标生成上下文包：汇总项目基础信息、招标文件版本、已确认矩阵项、证据摘录、无需绑定证据说明、风险确认记录、资格预评估结果和待补充事实。
2. 上下文包预览和审计：生成前允许用户查看模型将使用哪些内容，并记录上下文摘要、版本和来源。
3. 分章节提示词：投标函、法定代表人身份证明、授权委托书、资格响应、商务偏离表、承诺函、企业资质、人员、业绩等章节独立 prompt、独立 schema、独立回归样本。
4. 结构化商务标生成稿：输出章节、段落、表格和占位符，每个 block 标注覆盖的 `compliance_item_id`、引用证据和来源上下文。
5. 生成后校验：检查强制项覆盖率、证据引用完整性、项目名称/日期/单位名一致性、证书编号/人员/业绩事实和未确认内容。
6. 无证据内容拦截：缺资料或缺人工确认时输出待补充，不包装成已确认事实。

### 5.2 P1：商务标生成稿左右对照审阅

建议能力：

1. 商务标审阅工作台：左侧展示结构化商务标正文，右侧展示合规条目队列。
2. 双向定位：点击合规条目定位到左侧标书段落，点击标书段落定位到右侧覆盖条目。
3. 三层追溯：合规条目继续支持定位招标文件原文，标书段落可追溯到合规条目、招标原文和企业证据。
4. 覆盖状态：区分已覆盖、未覆盖、证据不足、生成内容待确认、无需写入正文但作为约束保留。
5. 审阅修改留痕：人工修改生成段落时记录差异、原因和影响的合规条目。
6. 审阅通过后导出 Word：Word 是交付格式，结构化稿是主要审阅对象。

## 6. MVP1.3：企业资料 RAG 和候选证据推荐

MVP1.3 的目标是增强 ContextPack 的上游证据来源：系统从企业资料库推荐候选证据，用户确认后再进入 ContextPack。它不直接替用户绑定证据，也不直接生成正式标书。

建议能力：

1. 企业资料真实 RAG：`BAAI/bge-large-zh-v1.5` embedding + pgvector + `BAAI/bge-reranker-large` 重排。
2. 企业资料索引重建：资料新增/更新后异步重建 1024 维向量索引。
3. 证据推荐解释增强：模型基于命中资料生成推荐理由，不自动绑定。
4. 企业资料语义匹配：比较招标要求和企业资料是否匹配，差异进入人工确认。
5. ContextPack 证据补全增强：按矩阵项、缺项和候选证据提示用户补齐上下文。
6. 企业资料改写：把证照、业绩、人员、承诺材料改写成标书语言。
7. 逐段证据引用：草稿段落必须标注引用来源。
8. 草稿事实校验增强：项目名、人员、证书编号、金额、日期、业绩名称等强校验。
9. 无证据内容拦截：无法验证事实必须标记人工确认。
10. Go/No-Go 建议增强：模型整理理由，但最终决策仍人工确认。
11. 实质性响应初判：强制项和否决项进入人工复核队列。

MVP1.2 / MVP1.3 必须保留的边界：

- 草稿不是正式标书。
- 无证据事实不得包装成已确认内容。
- 高风险条款、强制项、实质性响应必须人工确认。
- 导出 Word 时仍需保留内部草稿/正式版本边界。

## 7. 长期规划：净化行业闭环增强

净化设备/洁净工程行业闭环不排入具体 MVP 版本，待真实样本、产品目录、专业审核流程和责任边界明确后再拆专项，但仍坚持 AI 辅助而非自动承诺。

建议能力：

1. 净化产品目录 schema：设备型号、风量、过滤效率、洁净等级、压差、噪声、材质、尺寸、功率等。
2. 技术参数匹配：对比招标技术要求和产品目录。
3. 技术偏离分析：识别满足、偏离、缺参数和待确认项。
4. 候选设备推荐：生成候选配置表和理由。
5. 检测报告匹配：将检测报告指标绑定到技术响应项。
6. 安装调试验收方案草稿：基于历史方案和招标要求生成候选段落。
7. 技术标章节草稿：项目理解、技术响应方案、设备配置方案、安装调试验收方案、售后服务方案。
8. 投标阶段示意图辅助：系统框图、工艺流程图、简化设备布置示意图。

长期规划必须保留的边界：

- 产品选型只做候选推荐，不做最终工程承诺。
- 图纸只做投标阶段示意图，不替代正式设计图。
- 技术参数偏离必须人工确认。
- 最终技术方案必须由业务/技术负责人审核。

## 8. 明确禁止或长期不做的能力

以下能力不进入近期路线图：

1. 自动报名。
2. 自动签章。
3. 自动提交投标文件。
4. 自动替用户确认 Go/No-Go。
5. 自动通过审批任务。
6. 自动承诺产品参数、工期、金额、人员和证书信息。
7. 绕过人工确认直接修改正式投标文件。
8. 读取外部文件后自动执行高权限动作。

这些能力涉及法律责任、账号安全、CA/UKey、企业授权和投标合规风险，不适合作为 Agent 自动执行能力。

## 9. 上下文和审计要求

任何进入 MVP1.1 及之后的 AI 能力，都必须满足以下底线：

| 要求 | 说明 |
| --- | --- |
| 版本绑定 | 输出必须记录基于哪个招标文件解析版本 |
| 来源回链 | 条款、证据、草稿和风险必须能定位到原文或资料 |
| 证据引用 | 草稿生成必须保留引用资料 |
| 事实校验 | 金额、日期、证书编号、人员、业绩等事实必须校验 |
| 人工关口 | 高风险、强制项、实质性响应和最终决策必须人工确认 |
| 权限边界 | 模型不能自动审批、提交、签章或覆盖关键状态 |
| 审计日志 | 模型输入摘要、输出、证据、人工确认和后续动作必须留痕 |
| 非可信输入 | 外部网页、招标文件、附件和补遗都视为非可信输入 |

模型调用前应显式构建“生成上下文包”，至少标明：任务类型、目标章节、招标文件版本、相关矩阵项、可引用证据、不可用或待确认事实、风险提示、人工确认状态和输出格式约束。上下文包本身应可预览、可记录、可复盘。

## 10. 推荐版本路线

| 版本 | 核心目标 | AI 能力边界 |
| --- | --- | --- |
| MVP1.0 | 建好投标上下文工作台和可信闭环 | 已完成；不依赖自由聊天，以规则、检索、人工确认和审计为主 |
| MVP1.1 | AI 读标、拆分、分类、解释和审阅纠错 | P0 + P1 已完成主体开发；接 Chat/LLM、PromptOps 和模型配置中心，不接 embedding/rerank |
| MVP1.2 | 商务/资格草稿生成 ContextPack、分章节提示词、结构化生成稿和生成稿审阅 | 结构化稿必须回链合规条目、招标原文和已绑定证据，并经过事实校验和人工审阅 |
| MVP1.3 | 企业资料 RAG、Embedding/Rerank、候选证据推荐和人工绑定 | 检索结果只做候选证据，必须人工确认后才能进入 ContextPack |
| 长期规划 | PDF 原文式审阅、解析质量增强、净化行业闭环、多 Agent、OCR 和报价辅助 | 技术响应、参数匹配、候选配置、技术草稿和外部集成均需人工确认，暂不排入具体 MVP 版本 |

当前最重要的判断：

> 先把上下文做干净，再让 AI 进来；先让 AI 帮人定位和对比，再让 AI 帮人草拟；永远不要让 AI 直接替人做最终承诺。
